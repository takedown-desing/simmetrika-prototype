## 1. Моделирование интерпретации запроса поисковым ИИ (P01 Шаг 1)

Анализируемый «запрос»: `[ТИП СТРАНИЦЫ: корзина без оплаты + экран подтверждения, noindex] + [ЗАПРОС: отсутствует]`. Пояснение: поисковый ИИ эту пару страниц не должен видеть и цитировать; моделирование нужно, чтобы (а) краулер однозначно прочитал запрет индексации, (б) ИИ-ассистенты и антифрод-системы форм (Метрика, SmartCaptcha) корректно распознали страницу как шаг оформления, (в) структура совпала с ментальной моделью пользователя «корзина → контакты → подтверждение».

### 1.1 Сущности и атрибуты (NER)

1. **«Заявка»** — тип: Order-подобная сущность без оплаты (`lead`, CATALOG-MODEL §1). Атрибуты: номер, состав (`items[]`), контакт, статус, дата. Нормализованная форма: «список выбранных вариантов товаров + контакт покупателя».
2. **«Товар / вариант»** — тип: Product → ProductModel (вариант: ткань, цветовая группа, сторона угла, `sku`, `price`). В списке показывается именно вариант, не модель (ТЗ §4, §7).
3. **«Количество»** — атрибут позиции, целое 1–9; по умолчанию 1.
4. **«Ориентировочный итог»** — вычисляемый атрибут: сумма `price_snapshot × qty` по позициям с ценой; без цен не выводится `[ДОПУЩЕНИЕ Q-01]`.
5. **«Контакт»** — Person: имя, телефон (обязательно), email, удобный способ связи (звонок / WhatsApp / Telegram `[ДОПУЩЕНИЕ Q-10]`), комментарий, согласие на обработку данных (152-ФЗ → `/privacy/`).

### 1.2 Онтология и таксономия

1. Таксономическая ветка: Сайт → Служебные страницы → Шаг оформления (CheckoutPage-аналог) → Подтверждение. Не относится к каталогу, хотя содержит ссылки на товары.
2. Связи: `lead` → `variant` (N:M через `items[]`) → `product` → `category`; `lead` → `source_url` (страница, с которой пришли) → `utm_*` (первый источник сессии).
3. Отличие от «корзины» интернет-магазина: нет шага оплаты, нет расчёта доставки (ТЗ §12), итог только ориентировочный; следующая сущность после отправки не «заказ», а «звонок менеджера».
4. Смежные формы той же онтологии: `one_click` (один товар, модал на карточке), `question`, `callback` (home, kontakty). Все четыре — один тип `lead` с разным `type` (ТЗ §8).
5. Смежные страницы знаний: `/dostavka/` (сроки, оплата курьеру, предоплата 30% `[ДОПУЩЕНИЕ Q-02]`), `/kontakty/` (где посмотреть вживую), `/privacy/` (основание обработки).

### 1.3 Интент и фокус внимания (salience)

1. Основной интент: завершить действие, то есть «отправить список менеджеру и получить звонок». Вторичные: проверить состав, сравнить итог с бюджетом, убрать лишнее, сохранить список на потом (localStorage, ТЗ §7).
2. Наибольший вес на экране: поле «Телефон», кнопка «Отправить заявку», ориентировочный итог. Второй уровень: фото и название варианта, пометка «финальную стоимость согласует менеджер».
3. Главный риск отвала: сомнение «что произойдёт после отправки» и «будут ли звонить в неудобное время» → блок «Что будет после отправки» и поле «Удобный способ связи» стоят до кнопки.
4. На экране «Спасибо» фокус: номер заявки и срок звонка (1 час в рабочее время 10:00–21:00 `[ДОПУЩЕНИЕ Q-14]`); всё остальное вторично.

### 1.4 Внутреннее представление и ожидания ИИ

1. Нормализованная форма для краулера: «страница шага оформления, не предназначена для индексации, содержимое зависит от клиентского состояния» → `noindex,nofollow`, `X-Robots-Tag`, отсутствие в sitemap, отсутствие в `BreadcrumbList` и `ItemList` других страниц.
2. Чек-лист ожиданий пользователя (не ИИ): состав виден без скролла хотя бы первой позицией; итог и кнопка доступны в любой точке скролла; ошибки формы говорят, что исправить; после отправки есть номер и срок звонка.
3. Сигналы для антифрода форм и аналитики: один `POST` на одну отправку, капча, honeypot, события `ecommerce.purchase` только после подтверждённого ответа сервера.
4. Неоднозначность: URL `/zayavka/` без состояния (пустой localStorage) → пустое состояние с навигацией в каталог, не 404 и не редирект (пользователь мог открыть ссылку из шапки сознательно).
5. Уверенность: высокая, страница не участвует в ранжировании; единственный внешний риск — попадание URL `/zayavka/spasibo/?id=…` в индекс через шаринг ссылки, что закрыто `noindex` + `sig`.

## 2. Прикладные рекомендации (P01 Шаг 2)

### 2.1 Содержание: сущности, атрибуты, связи

1. Каждая позиция списка раскрывает вариант полностью: фото варианта, «{Тип} диван {Модель}» + категория, строка варианта «{материал} {коллекция}, {цвет}{, сторона}», артикул `sku`, цена варианта или «по запросу» `[ДОПУЩЕНИЕ Q-01]`, статус наличия «В наличии» / «Под заказ {lead_time_days} дн.» `[ДОПУЩЕНИЕ Q-02]`, количество, ссылка на карточку с `?variant={sku}` (CATALOG-MODEL §2).
2. Итог: только по позициям с ценой, подпись «Ориентировочно, без доставки. Финальную стоимость согласует менеджер». Если ни у одной позиции нет цены, блок итога заменяется строкой «Цены уточнит менеджер».
3. Форма: ровно поля ТЗ §8 + одно поле «Удобный способ связи» (звонок / WhatsApp / Telegram) `[ДОПУЩЕНИЕ Q-10]`; скрытые `type=cart`, `items[]`, `source_url`, `utm_*`.
4. Связи после отправки: номер заявки ↔ письмо менеджеру ↔ запись в БД ↔ событие аналитики с тем же `id`.
5. Нигде на странице не появляются цифры доставки и сроков, кроме как ссылкой на `/dostavka/` и короткой строкой статуса позиции: страница не должна дублировать `/dostavka/`.

### 2.2 Структура страницы

1. `/zayavka/`: H1 → список (H2) → итог (H2) → форма (H2) → «Что будет после отправки» (H2, три шага) → короткий FAQ (H2, 10 вопросов в аккордеоне, без `FAQPage`). Mid-content CTA не нужен: вся страница и есть CTA; вместо него sticky-итог.
2. Пустое состояние: H1 → H2 «В заявке пока ничего нет» → плитки категорий + `/catalog/v-nalichii/` + `/sale/` → форма «Обратный звонок» не показываем (есть в шапке), чтобы не плодить лиды без товаров.
3. `/zayavka/spasibo/`: H1 с номером → срок звонка → H2 «Что дальше» (3 шага) → H2 «Пока ждёте звонка» (ссылки) → телефон.
4. Элементы: таблица-список позиций (на мобильном — карточки), числовой степпер, форма с `fieldset`, список шагов `<ol>`, аккордеон FAQ `<details>`.

### 2.3 Тип контента / формат

Интерактивная утилитарная страница: 80% интерфейса, 20% микрокопи. Никакого SEO-текста, никаких описательных абзацев; каждая строка текста либо подпись к элементу, либо ответ на сомнение перед отправкой. Экран «Спасибо» — статичная страница с серверным рендером по `id`.

## 5. FAQ (10 Q/A, аккордеон на `/zayavka/`, без FAQPage)

1. **Что будет после того, как я отправлю заявку?**
   Заготовка: менеджер перезвонит в течение 1 часа в рабочее время 10:00–21:00, уточнит ткань, сторону и количество, назовёт точную цену и срок. Источник: `_CONTEXT §2` `[ДОПУЩЕНИЕ Q-14]`.
2. **Это покупка? Нужно ли платить на сайте?**
   Заготовка: нет, онлайн-оплаты на сайте нет; заявка — это список для менеджера, оплата при получении или по счёту после согласования. Источник: `_CONTEXT §1, §7` `[ДОПУЩЕНИЕ Q-02]`.
3. **Почему итог «ориентировочный»?**
   Заготовка: цены указаны «от» для варианта ткани; финальная стоимость зависит от выбранной ткани, стороны и размера и подтверждается менеджером. Источник: `_CONTEXT §8`, QUESTIONS Q-01 `[ДОПУЩЕНИЕ Q-01]`.
4. **Можно ли изменить состав заявки после отправки?**
   Заготовка: да, при звонке менеджера можно добавить или убрать позиции, сменить ткань или количество. Источник: ТЗ §7 (ручная обработка менеджером).
5. **Сохранится ли список, если я закрою сайт?**
   Заготовка: да, список хранится в этом браузере 30 дней без регистрации; на другом устройстве его не будет. Источник: ТЗ §7 (localStorage), срок — решение разработки (13.2).
6. **Нужна ли предоплата?**
   Заготовка: при заказе под индивидуальный размер — предоплата 30%, для моделей из каталога оплата при получении или по счёту. Источник: `_CONTEXT §7` `[ДОПУЩЕНИЕ Q-02]`.
7. **Сколько ждать диван?**
   Заготовка: в наличии — доставка 1–3 дня, под заказ — изготовление 14–21 день; срок по каждой позиции менеджер подтвердит при звонке. Источник: `_CONTEXT §7` `[ДОПУЩЕНИЕ Q-02]`; ссылка `/dostavka/`.
8. **Можно ли сначала посмотреть диван вживую?**
   Заготовка: да, 5 шоурумов в Москве и Химках, адреса и часы на странице контактов; скажите менеджеру, в какой точке удобно. Источник: `_CONTEXT §5` `[ДОПУЩЕНИЕ Q-09]`; ссылка `/kontakty/`.
9. **Почему у позиции нет цены?**
   Заготовка: для части тканей цена рассчитывается индивидуально; менеджер назовёт её при звонке. Источник: product.md §13 п.1–2 `[ДОПУЩЕНИЕ Q-01]`.
10. **Как вы используете мой телефон и email?**
    Заготовка: только для связи по этой заявке; основание и сроки хранения описаны в политике конфиденциальности. Источник: ТЗ §11 (152-ФЗ); ссылка `/privacy/` `[ДОПУЩЕНИЕ Q-11]`.

Напоминание: `FAQPage` на этой странице не ставится (noindex, раздел 6); ответы остаются 1–2 предложениями, без цифр сверх `_CONTEXT.md`.

Только `WebPage` (с указанием `Organization` по `@id`, узел которой выводится общим шаблоном на всех страницах по CATALOG-MODEL §4). Черновик для `/zayavka/`:

```json
      "sameAs": ["https://vk.com/club177326997"]
    },
    {
      "@type": "WebPage",
      "@id": "https://simmetrika-mebel.ru/zayavka/#webpage",
      "url": "https://simmetrika-mebel.ru/zayavka/",
      "name": "Ваша заявка | SIMMETRIKA",
      "inLanguage": "ru-RU",
      "isPartOf": { "@id": "https://simmetrika-mebel.ru/#website" },

```

Для `/zayavka/spasibo/` тот же граф с `@id` `https://simmetrika-mebel.ru/zayavka/spasibo/#webpage`, `url` без параметров `id`/`sig`, `name` «Заявка принята | SIMMETRIKA». Узел `Organization` здесь сокращён: полный (адрес, `contactPoint`, `location`) живёт в общем шаблоне (kontakty.md раздел 6) и не дублируется.

Чего нет и почему:

- `BreadcrumbList`: страница `noindex,nofollow`, в выдаче крошки не показываются; визуальные крошки остаются для навигации.
- `FAQPage`: расширенные сниппеты не выдаются noindex-страницам; дублировать 10 Q/A в JSON-LD без выигрыша в поиске — лишний вес HTML и риск рассинхрона с текстом.
- `CheckoutPage` (подтип `WebPage`): допустимо как `"@type": ["WebPage", "CheckoutPage"]`, но не даёт ничего для noindex-страницы; оставлено как необязательная опция для разработчика.

- `LocalBusiness` ×5: только на `/kontakty/` (CATALOG-MODEL §4).
- Персональные данные покупателя в разметку не попадают ни в каком виде.

## 11. Доступность

- Один H1 на каждой странице; иерархия H1 → H2 → H3 без пропусков (H3 позиций вложены в H2 «Выбранные диваны»).
- Landmarks: `header`, `nav` (крошки `aria-label="Хлебные крошки"`), `main` (H1 внутри), `aside` для sticky-колонки итога на desktop (`aria-label="Итог заявки"`), `footer`. Sticky-полоса на mobile — `div role="region" aria-label="Итог и отправка"`.
- Список позиций: `<ul>` с `<li>` на позицию (mobile) или `<table>` с `<caption>` «Выбранные диваны» и `<th scope="col">` (desktop). Степпер: `<button aria-label="Уменьшить количество, {Модель}">`, `<input type="number" min=1 max=9 inputmode=numeric aria-label="Количество, {Модель}">`, `<button aria-label="Увеличить количество, {Модель}">`; кнопка «Удалить» с текстом «Удалить {Модель} из заявки» (визуально иконка + «Удалить»).
- Изменение итога после ± и удаления объявляется через `aria-live="polite"` в блоке итога («Итого ориентировочно {sum} ₽, {N} позиций»); не чаще одного объявления на 500 мс (debounce).
- Форма: `<label for>` у каждого поля, обязательность — текстом «(обязательно)» в label + `aria-required`; `autocomplete` (`name`, `tel`, `email`), `inputmode="tel"`; ошибки: текст под полем, связанный через `aria-describedby`, `aria-invalid="true"`, сводка ошибок над кнопкой в `aria-live="assertive"` («Исправьте 2 поля: телефон, согласие»); фокус переводится на первое невалидное поле; цвет ошибки дублируется иконкой и текстом.
- Чекбокс согласия: ссылка на `/privacy/` внутри `label`, открывается в новой вкладке с `aria-label="Политика конфиденциальности, откроется в новой вкладке"`.
- Радиогруппа способа связи: `<fieldset><legend>Как с вами связаться</legend>`, стрелки переключают.
- Капча: невидимый режим; при показе челленджа — текстовая альтернатива провайдера; honeypot недоступен для клавиатуры и скринридера (`aria-hidden`, `tabindex=-1`).
- Кнопка отправки: во время запроса `aria-busy="true"`, текст «Отправляем…», `disabled`; после ошибки сети фокус на сообщение об ошибке.
- Тост «удалено / вернуть»: `role="status"`, кнопка «Вернуть» доступна с клавиатуры, таймер 6 с ставится на паузу при фокусе.
- `OneClickModal`: `<dialog>` с `aria-labelledby` на заголовок, ловушка фокуса, `Esc` закрывает, возврат фокуса на кнопку-инициатор, фон `inert`.
- Экран «Спасибо»: H1 получает фокус при загрузке (`tabindex="-1"`), чтобы скринридер зачитал номер; телефон — `<a href="tel:">` с полным номером в тексте.
- Тап-цели ≥ 44 px (степпер 44×44, «Удалить» 44 px, чипы 40 px высота + отступ); `:focus-visible` контрастная обводка 2 px; контраст текста ≥ 4.5:1, цены и ошибок ≥ 4.5:1.
- Печать: `@media print` скрывает шапку, футер, sticky, капчу; таблица позиций и итог печатаются (покупатель может взять список в шоурум).
- Цель Lighthouse: Accessibility ≥ 95, Best Practices ≥ 95; Performance ≥ 90 (без тяжёлых изображений, капча грузится лениво при фокусе на первом поле формы).

## 13. Особые случаи (UX-спецификация)

### 13.1 Хранилище заявки (localStorage)

- Ключ: `simmetrika_lead_v1` (версия в имени ключа; при смене схемы — новый ключ + миграция старого).
- Схема JSON:

```json
{
  "v": 1,
  "updated_at": "2026-10-13T12:00:00+03:00",
  "source_url": "/catalog/uglovye-divany/reymond/",
  "utm": { "utm_source": "", "utm_medium": "", "utm_campaign": "", "utm_term": "", "utm_content": "", "captured_at": "" },
  "items": [
    {
      "variant_id": 0,
      "sku": "{variant.sku}",
      "product_id": 0,
      "product_url": "/catalog/{category}/{slug}/",
      "name": "{Тип} диван {Модель}",
      "category": "{category.name}",
      "variant_label": "{material} {fabric.name}, {color_group}{, left|right}",
      "fabric": "{fabric.name}",
      "color_group": "{color_group}",
      "side": "left|right|null",
      "price_snapshot": 0,
      "availability": "in_stock|made_to_order",
      "lead_time_days": 0,
      "thumb": "/img/{file}.webp",
      "qty": 1,
      "added_at": "2026-10-13T12:00:00+03:00"
    }
  ]
}
```

- `price_snapshot` — `variant.price` на момент добавления (`null`, если цены нет `[ДОПУЩЕНИЕ Q-01]`). `source_url` — страница первого добавления (для `lead.source_url`). `utm` — первый касание в сессии (first-touch), пишется при любом заходе с `utm_*`, не перезаписывается, если уже есть.
- Срок жизни: 30 дней от `updated_at`; при загрузке любой страницы устаревший объект удаляется, счётчик = 0. Лимит: 20 позиций; при попытке добавить 21-ю — тост «В заявке максимум 20 позиций». Максимум `qty` = 9.
- Повторное добавление того же `variant_id`: `qty + 1` (до 9), не новая строка; тост «Количество увеличено: {qty}».
- Счётчик в шапке: `items.length` (число позиций, не сумма `qty`; согласовано с home.md блок 1). Обновление во всех вкладках через событие `storage`; в текущей вкладке — через кастомное событие `lead:changed`. Бейдж скрыт при 0.
- Отключённый localStorage (приватный режим, запрет cookies): fallback на `sessionStorage`, затем на память вкладки; при недоступности обоих — тост «Браузер не сохраняет список. Закажите в один клик или позвоните {телефон}».
- Персональные данные (имя, телефон, email) в localStorage не сохраняются. Черновик формы — только в `sessionStorage` на время вкладки, стирается после отправки.

### 13.2 Загрузка `/zayavka/` и актуализация

- Рендер списка из localStorage мгновенно (без ожидания сети), затем `GET /api/lead/refresh?ids={variant_id,...}` → сервер возвращает для каждого `variant_id`: `is_active`, `price`, `availability`, `lead_time_days`, `thumb`, `product_url`, `name`, `variant_label`.
- Таймаут 4 с; при ошибке — блок 4 «Не удалось проверить цены, показаны сохранённые», отправка остаётся возможной (сервер пересчитает).
- Скелетоны вместо прыжков макета: высота строки фиксирована до ответа.

### 13.3 Слияние при изменении цен и наличия

- Цена изменилась: `price_snapshot` заменяется серверной; в строке позиции на 1 сессию показывается «было {old} ₽» зачёркнуто; блок 4: «Цена обновлена по {N} позициям». Старое значение передаётся в `items[].price_client` при отправке для истории.
- Вариант неактивен (`is_active=false`) или товар выключен: строка остаётся с пометкой «Снят с продажи», без степпера, не входит в итог и в `items[]` отправки; кнопка «Удалить» и ссылка «Другие исполнения» → `product_url` (там сработает 301/410 по product.md §13 п.4). Через 7 дней такая позиция удаляется автоматически.
- Изменились наличие/срок: обновляются тихо, без уведомления.
- Цена появилась у позиции, где было «по запросу»: обновляется, уведомление как при изменении.
- Сервер при `POST /api/lead` заново читает `variant.price` и сохраняет оба значения: `price_snapshot` (клиент) и `price_server`; письмо менеджеру показывает серверное и помечает расхождение.

### 13.4 Состояние «нет цены» `[ДОПУЩЕНИЕ Q-01]`

- Позиция без цены: «по запросу», сумма строки пустая, в итог не входит, счётчик «{M} позиций без цены: уточнит менеджер».
- Все позиции без цены (Q-01 = «не публикуем»): блок итога заменяется строкой «Цены уточнит менеджер», sticky-полоса показывает «{N} позиций · Отправить заявку», `ecommerce.purchase` отправляется с `price: 0` опущенным (без поля), `value` в GA4 не передаётся.

### 13.5 Количество, удаление, восстановление

- Степпер `−`/`+` с мгновенным пересчётом; `−` при `qty=1` неактивен (удаление только кнопкой «Удалить», чтобы не терять позицию случайно). Ручной ввод в поле: только цифры 1–9, иное сбрасывается на предыдущее.
- Удаление: позиция скрывается, тост «Вернуть» 6 с; окончательная запись в localStorage по таймеру или при уходе со страницы (`pagehide`). Аналитика: `ecommerce.remove` / `remove_from_cart` после окончательного удаления, не при нажатии.
- Удаление последней позиции → переход в пустое состояние без перезагрузки; sticky и форма скрываются; введённые в форму данные сохраняются в `sessionStorage` на случай возврата.

### 13.6 Валидация и тексты ошибок

Проверка на `blur` поля и при отправке; сообщения без извинений, формулировка «что исправить»:

| Поле | Правило | Текст ошибки |
|---|---|---|
| Имя | 2–60 символов, буквы, пробел, дефис | «Укажите имя» / «Имя: только буквы, от 2 символов» |
| Телефон | маска `+7 (___) ___-__-__`; принимает ввод с `8`, `7`, `+7`; нормализация в `+7XXXXXXXXXX`; 10 цифр после +7, первая 3, 4, 8 или 9 | «Введите телефон полностью: +7 (999) 123-45-67» |
| Email | необязательно; если заполнено — формат `x@y.z` | «Проверьте email: нужен символ @ и домен» |
| Способ связи | одно из 3 значений, по умолчанию `call` | ошибка невозможна |
| Комментарий | ≤ 1000 символов, счётчик «{n}/1000» | «Сократите комментарий до 1000 символов» |
| Согласие | обязательно | «Отметьте согласие на обработку данных» |
| Капча | токен провайдера | «Пройдите проверку: нажмите «Я не робот»» |
| Состав | ≥ 1 активной позиции | «Добавьте хотя бы один диван: список пуст» (кнопка неактивна до этого) |

| Сервер 5xx / сеть | — | «Заявка не отправилась. Попробуйте ещё раз или позвоните +7 929 677-78-75» `[ДОПУЩЕНИЕ Q-10]`, данные формы сохранены |

- Кнопка не блокируется до первой попытки (чтобы не прятать причину); после попытки с ошибками — активна, повторная проверка на каждом изменении.

### 13.7 Капча и антибот

- Провайдер: Яндекс SmartCaptcha в невидимом режиме (доступен в РФ, не требует сторонних доменов, которые могут блокироваться) — решение разработки, вынесено в раздел 14 NEW-4. Скрипт грузится лениво при первом фокусе в форме.
- Дополнительно: honeypot-поле `website` (заполнено → 200 OK без записи, чтобы не подсказывать боту), проверка времени между открытием формы и отправкой (< 3 с → мягкая проверка капчей), серверная проверка токена.

### 13.8 Дубль-защита и троттлинг

- `submission_id` (UUID v4) генерируется при открытии формы, хранится в `sessionStorage`, передаётся в `POST`; сервер хранит `submission_id` 24 часа: повторный `POST` с тем же id возвращает тот же `lead.id` без новой записи и письма (идемпотентность при двойном клике, повторе из-за таймаута, кнопке «Назад»).
- Кнопка `disabled` + `aria-busy` с момента отправки до ответа; повторный клик игнорируется.
- Семантический дубль: тот же нормализованный телефон + тот же набор `variant_id` в течение 10 минут → сервер отвечает 200 с тем же номером заявки и флагом `duplicate=true`; клиент ведёт на `/zayavka/spasibo/` того же `id`; письмо не дублируется, в БД `duplicate_of` ссылается на первую.
- Троттлинг: не более 3 заявок за 10 минут с одного IP или телефона и 20 за сутки → 429 с текстом из 13.6; `Retry-After` в заголовке.
- Для `one_click` и `cart` правила общие; `callback`/`question` — те же лимиты.

### 13.9 «Заказать в один клик» (отличия, подробно в 4.4)

- Живёт в карточке товара (product.md блок 19), вызывается из `BuyPanel`, `MidCta`, `StickyBuyBar`.
- `type=one_click`, одна позиция с `qty=1`, `price_snapshot` выбранного варианта; список в localStorage не меняется.
- Минимальная форма: имя, телефон, согласие, капча. Успех — в модале, без редиректа; номер заявки показывается в модале; цель `lead_one_click`.
- Если в localStorage уже есть позиции, модал внизу показывает строку «В заявке ещё {N} позиций. Отправить всё вместе» → ссылка на `/zayavka/` (добавляет текущий вариант в список перед переходом).

### 13.10 Отправка, очистка и редирект

- `POST /api/lead` JSON: `{type, name, phone, email, contact_method, comment, consent: true, captcha_token, submission_id, items: [{variant_id, sku, qty, price_snapshot}], source_url, utm: {...}, referrer, ym_client_id, ga_client_id}`. Ответ: `{id, number, sig, items_count, duplicate}`.
- Последовательность при успехе: 1) `sessionStorage` ← `simmetrika_last_lead = {id, number, sig, items, total}` (для аналитики на следующей странице); 2) localStorage `items = []`, `updated_at` обновлён, `utm` сохраняется (следующая заявка с тем же источником); 3) событие `lead:changed` → счётчик в шапке 0; 4) переход `location.assign('/zayavka/spasibo/?id={number}&sig={sig}')`.
- Почему отдельная страница, а не модал: (а) цель Метрики и GA4 дублируется условием «посещение URL /zayavka/spasibo/» — страховка, если dataLayer-событие потеряется; (б) кнопка «Назад» возвращает на пустую заявку, а не на форму с данными (без повторной отправки); (в) страница печатается и пересылается (номер заявки); (г) серверный рендер по `id` гарантирует, что показан номер реальной записи; (д) для `one_click` модал оправдан: один товар, пользователь остаётся на карточке.
- Серверный вариант без JS: обычный `POST` формы → 303 Redirect на ту же `/zayavka/spasibo/?id&sig`; список при этом очистить нельзя (нет JS) — экран «Спасибо» содержит `<script>` очистки, а при отсутствии JS — строка «Список в заявке можно очистить вручную».

### 13.11 Номер заявки и подпись

- `lead.number` — публичный номер: год + порядковый, формат `2026-000123` (6 цифр, ведущие нули); `lead.id` внутренний автоинкремент. В H1 и письме — `number`.
- `sig` = HMAC-SHA256(`number`, серверный секрет), 16 hex-символов. Защищает от перебора номеров; срок действия ссылки — 7 дней (после — 302 на `/catalog/`).

### 13.12 Защита экрана «Спасибо» от прямого захода

- Нет `id` или `sig`, подпись не сходится, срок истёк, заявка не найдена → `302` на `/catalog/` (без сообщения: прямой заход без контекста). Логировать как `thanks_guard_redirect`.
- `id` валиден → 200, `Cache-Control: no-store, private`, рендер: `number`, `items_count`, `created_at`, рабочие часы.
- Вне рабочих часов (МСК, 21:00–10:00): строка срока звонка меняется на «Перезвоним после 10:00» `[ДОПУЩЕНИЕ Q-14]`; выходные не учитываются (часы ежедневные, `_CONTEXT §5`).
- Повторное открытие той же ссылки в течение 7 дней: страница та же, аналитика не дублируется (13.13).

### 13.13 Аналитика (ТЗ §10, CATALOG-MODEL §5)

- Все события через `window.dataLayer` в формате Яндекс.Метрики (`ecommerce`) + GA4 (`event`), счётчики создаются новые `[ДОПУЩЕНИЕ Q-13]`.
- `/zayavka/` просмотр: GA4 `view_cart`, Метрика без ecommerce-события (нет аналога), параметр визита `lead_items = N`.
- ±: без событий (шум); удаление окончательное: Метрика `ecommerce.remove`, GA4 `remove_from_cart` (product.md §13 п.14).
- Начало заполнения формы (первый фокус): GA4 `begin_checkout` с `items[]`; Метрика цель `lead_cart_form_start` (вспомогательная).
- Успешная отправка `type=cart`: событие `purchase` отправляется на `/zayavka/spasibo/` из `sessionStorage.simmetrika_last_lead` при загрузке страницы (надёжнее, чем перед редиректом: нет гонки с `location.assign`). Метрика: `ecommerce.purchase` `{actionField: {id: number, revenue: total}, products: [{id: sku, name, brand: "SIMMETRIKA", category, variant: variant_label, price, quantity: qty}]}`; GA4: `purchase` `{transaction_id: number, value: total, currency: "RUB", items: [...]}`. Цель Метрики `lead_cart` (JS-событие `reachGoal('lead_cart', {number, items_count, total})`); резервная цель «посещение URL содержит /zayavka/spasibo/».
- Дедупликация: после отправки `purchase` ставится `sessionStorage.purchase_sent_{number}=1`; при перезагрузке страницы событие не повторяется. Это уточняет product.md §13 п.14 («отправка заявки из /zayavka/»): событие остаётся одно, место отправки — экран «Спасибо».
- `type=one_click`: `purchase` + цель `lead_one_click` отправляются из модала по ответу сервера (редиректа нет); дедуп по `submission_id`.
- Ошибки: GA4 `form_error` `{form: "cart", field}`; 429 и 5xx — `form_submit_failed`.
- `ym_client_id`/`ga_client_id` уходят в `lead` для сквозной аналитики без CRM (ТЗ §10: CRM вне скоупа).

### 13.15 Прочие состояния

- **JS отключён**: список не читается из localStorage → страница показывает пустое состояние + строка «Для работы заявки включите JavaScript или позвоните {телефон}»; форма «Обратный звонок» в шапке работает серверным `POST`.
- **Несколько вкладок**: изменение в одной вкладке обновляет список и счётчик в другой (`storage`); отправка в одной вкладке очищает список во всех.
- **Кнопка «Назад» с экрана «Спасибо»**: открывается `/zayavka/` в пустом состоянии (список уже очищен); `bfcache` отключён для `/zayavka/` (`Cache-Control: no-store`), чтобы не показать устаревший список.
- **Пагинация / сортировка / фильтры**: не применимы; список до 20 позиций без пагинации.
- **Local (NAP)**: телефон и часы в `PhoneOrderStrip` и на экране «Спасибо» из `_CONTEXT §2, §5` `[ДОПУЩЕНИЕ Q-09, Q-10]`; без `LocalBusiness`.
- **Вариант без фото**: обложка модели + точка (product.md §13 п.3), alt без ткани.
- **Снятый с продажи товар**: 13.3.
- **Ссылка `/zayavka/` из письма или мессенджера**: откроется пустое состояние на другом устройстве (localStorage локален) — строка в пустом состоянии объясняет «список сохранится в этом браузере».
